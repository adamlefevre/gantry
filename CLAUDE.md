## Commands

TypeScript control plane (npm workspaces; root `package.json` workspaces = `apps/*`). The Makefile wraps these (`make test`, `typecheck`, `dev`, `deploy`, `modal-deploy`); it uses `SHELL := /bin/bash`, so on Windows run it from Git Bash.

- `npm test` (root) or `npm --prefix apps/control-plane run test` → `vitest run`. Fully offline: Miniflare plus mock Modal, GitHub and Anthropic HTTP servers.
- Single test: `cd apps/control-plane && npx vitest run -t "<test name substring>"`
- `npm --prefix apps/control-plane run dev` / `deploy` → `wrangler dev` / `wrangler deploy`
- Type-check: `cd apps/control-plane && npx tsc --noEmit` (there's no lint script)
- `make modal-deploy` deploys the execution sandbox (`modal deploy services/execution-sandbox/service.py`); `requirements.txt` holds the Python deps for that.
- `make sandbox-test` runs the sandbox service's offline tests (`services/execution-sandbox/tests`, deps in `services/execution-sandbox/requirements-test.txt`). `tests/conftest.py` swaps in a fake `modal` package, so they need no Modal account and never call Modal.

CI (`.github/workflows/ci.yml`) runs the type-check and the offline tests on Node 22, and the sandbox service tests on Python 3.11. It needs no secrets. Both workflows pin actions to commit SHAs (Dependabot updates them) and run `npm ci --ignore-scripts`; keep new steps the same way. The Deploy workflow (`.github/workflows/deploy.yml`) deploys both services from GitHub when someone runs it, using repository secrets; see `docs/deploy.md`.

The lakehouse (R2 ingest, compaction, the Modal cron) lives in the separate gantry-lakehouse repo (ADR 0003). The only link is the telemetry the control plane writes to R2; its shape and path are the contract in `docs/telemetry.md`. If you change `AgentTelemetry` or the telemetry key, update that file and bump its version.

Deploying (Modal, Cloudflare, secrets) and the first live run on gantry-lakehouse: `docs/deploy.md`. `scripts/smoke-task.sh owner/name <issue>` starts one issue task on the deployed Worker and checks that its telemetry, with a non-empty patch, reached R2.

## Architecture

### Control plane (TypeScript, `apps/control-plane`)
- Request flow: `src/index.ts` (Worker router) → `TaskCoordinator` Durable Object, one per task via `idFromName(taskId)` → `runAgentLoop` in `src/agent.ts` → Modal sandbox HTTP API.
- Routes: `POST /api/tasks/:id/start`, `GET /api/tasks/:id/{status,steps,ws}`. The router rewrites each to a bare DO path (`/start`, `/status`, ...) before forwarding.
- Every `/api` route needs `Authorization: Bearer <GANTRY_API_TOKEN>` (a Worker secret), checked in `src/index.ts` before routing. With no token configured the Worker refuses all `/api` requests (fail closed). The tests send the token by default; the "API token" tests use `rawDispatch` to control the header.
- `/start` takes an **issue task** (`{repo: "owner/name", issue: 12}` or `{issue: "<github issue URL>"}`, optional `ref` and `prompt`) or a **prompt task** (`{prompt, repoUrl?, ref?}`). `src/taskInput.ts` resolves it inside the DO; `src/github.ts` fetches the issue from the unauthenticated GitHub REST API (`GITHUB_API_URL` overrides the base, `GITHUB_TOKEN` is the seam for the step-3 App token) and fences the issue text into the prompt. Bad input returns 400/404/422/503 and creates no task row. Repo tasks must target `https://github.com/owner/name` on `GANTRY_ALLOWED_REPOS` (`src/repoPolicy.ts`: 403 otherwise, checked before the issue fetch; empty list refuses every repo task), and `ref` can't be a `refs/...` name (400); the sandbox service repeats both checks. The task row keeps `issue_updated_at`, `issue_sha256` and `commit_sha`, and telemetry carries `commitSha`. A `/start` for a task ID whose loop is still running in that Durable Object returns 409 (an in-memory flag, so a task left RUNNING by a restart can be started again).
- `TaskCoordinator` uses DO SQLite (tables `tasks` and `steps`, migration tag `v1` in `wrangler.jsonc`; new `tasks` columns go in the `PRAGMA table_info` + `ALTER TABLE ADD COLUMN` list in `initDatabase`) and hibernatable WebSockets to broadcast `TASK_STARTED` / `AGENT_STEP` / `THOUGHT_STREAM` / `TASK_CONFIG` / `TASK_ERROR` / `TASK_FINISHED`. It runs the agent session in `ctx.waitUntil` and writes telemetry JSON to the `GANTRY_BUCKET` R2 binding.
- `agent.ts` runs its own loop on the official Anthropic SDK (`@anthropic-ai/sdk`, secret `ANTHROPIC_API_KEY`; ADR 0005): one `client.beta.messages.create` per turn. Its system prompt, tool descriptions, model (`claude-opus-5-5`), effort (`high`) and budgets (16 turns, an optional token cap, timeouts) come from `apps/control-plane/agent-config.json`, validated by `src/agentConfig.ts` (ADR 0006, `docs/agent-config.md`); bump its `version` when you change it, since every run's telemetry and task row record the version and a hash of the config used. The `GANTRY_MODEL` and `GANTRY_EFFORT` vars override model and effort. It uses adaptive thinking, top-level prompt caching and server-side refusal fallbacks. Each assistant turn goes back unchanged, thinking blocks included, and a turn's tool results go back together in one user message. Don't add `tool_choice` or `temperature`: Opus 5.5 rejects both. Its tools are `runCommand`, `readFile` (paged, line-numbered), `editFile` (exact-text replacement), `writeFile` (an existing file must be read first), `getDiff`, plus `runTests` when the repo declares a test command. The file tools live in `src/tools/` (adapted from eve; see `NOTICE`) and return errors to the model as `{error}`. Input that fails a tool's zod schema, or an unknown tool, goes back as an `is_error` result. A thrown error from `runCommand`, `getDiff` or `runTests` (a sandbox failure) fails the task, and so does a refusal. It calls `/session/create`, then reads `.gantry.yml` via `/file/read` (404 = absent), parses it in the Worker (`src/gantryConfig.ts`, ADR 0002), runs each `setup` command through `/exec` (non-zero exit fails the task), and only then starts the loop. `/session/terminate` runs in a `finally`. Both `getDiff` and the final patch run `DIFF_COMMAND` (`git add --all --intent-to-add && git diff`), so new files are in the patch.
- A task's `verification` is `unverified` (no `test:`; draft PRs only) or `pending` (step 4's red-green verification will decide). It's null until `.gantry.yml` has been read. See `GLOSSARY.md`.
- Sandbox wire contract: the agent sends both `sessionId` and `sandbox_id` with a `Bearer AGENT_SANDBOX_TOKEN` header, and accepts either key from `/session/create`. Endpoints: `/session/create`, `/exec`, `/file/write`, `/file/read`, `/session/terminate`. If you change the contract, update `services/execution-sandbox/service.py`, `agent.ts`, and `tests/mock-modal-server.ts` together.
- Tests (`apps/control-plane/tests/control-plane.test.ts`) bundle `src/index.ts` with esbuild (`cloudflare:workers` external) and load it into Miniflare with DO + R2 bindings. The mock Modal and Anthropic servers live at the repo root (`tests/mock-modal-server.ts`, `tests/mock-anthropic-server.ts`) and are re-exported from `apps/control-plane/tests/`. `ANTHROPIC_BASE_URL` points the agent at the mock Messages API, which picks a scripted sequence of model turns by a marker in the task prompt (`anthropicServer.script(marker, turns)`); an unscripted prompt gets "Done." on its first turn. Every mock reply starts with a thinking block, and `toolResultsIn(request)` reads the tool results a request sent back.

### Execution sandbox (`services/execution-sandbox/service.py`)
- Modal app `agent-sandbox-service`: a FastAPI app served via `@modal.asgi_app(label="sandbox-service")`, so its URL is `https://<workspace>--sandbox-service.modal.run`. The endpoint function's `timeout` (960 s) must stay above the longest `/exec` timeout, and `@modal.concurrent` lets one container serve several requests. Sandboxes are created without `app=`, so Modal attaches them to the deployed app. It authenticates against the Modal secret `agent-sandbox-secret` (rejects all requests if unset), creates `modal.Sandbox` instances (Debian, Python 3.11, git, pytest and ruff; anything else a target repo needs comes from its `.gantry.yml` `setup:`) and re-attaches to them with `Sandbox.from_id`.
- `/session/create` takes optional `{repo_url, ref}` (`https://github.com/owner/name` only for now; `ref` is a branch, tag or SHA, not a `refs/...` name, default `HEAD`) and shallow-fetches it into `/workspace`. Every later command and file path runs relative to `/workspace`. If the checkout fails, it terminates the sandbox and returns a 422.
- Untrusted input never goes through a shell, except the agent's own `/exec` command: git, `head` (for `/file/read`, capped at 1 MiB) and the file-write helper get argv, and file content goes over stdin.
- The resolved repo URL and `ref` are stored on the `tasks` row and forwarded to `/session/create`. Sandboxes live up to 30 minutes; `/exec` accepts `timeout_seconds` up to 900 (setup and test commands use 600).
- Design direction (our own Vercel AI SDK agent loop, GitHub App, red-green verification, `.gantry.yml`): `docs/adr/0001-software-factory-for-any-repo.md`.
